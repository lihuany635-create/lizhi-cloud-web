## 一、結論

1. **Switch 排除。** 它的授權是 Apache 2.0 加 Commons Clause，不符合 OSI 對開源的定義。
2. **最接近你構想的開源專案是 `agentchattr`（MIT）。** 它是一個群組聊天室，你、Claude Code、Codex、Gemini CLI 都在裡面。AI 之間可以互相 @ 並觸發對方，有防迴圈上限（預設 4 跳），聊天訊息可以轉成「工作（Job）」，**而且支援 Windows**，你現在的電腦就能測。
3. **它缺的部分：** 只能在本機使用，沒有手機版、沒有遠端登入；沒有 GitHub PR 和審查的正式流程；沒有「等待你核准」的關卡。這些要自己補。
4. **訂閱可以用。** agentchattr 啟動的是官方原版的 Claude Code 和 Codex CLI，再把訊息打進它們的終端機，所以用的是你自己的訂閱登入，符合 Anthropic「用自己的訂閱登入未修改的 Claude Code」的條款。
5. **建議路線：**
   - P1 先用 agentchattr 在你的 Windows 電腦上實測。
   - 測過以後，決定要「擴充 agentchattr」，還是「改用 Matrix 聊天室，自己寫代理橋接」（這條才有手機版和遠端存取）。

## 三、agentchattr 詳細核對（第一候選）

來源：README（MIT，約 1.6k stars、175 commits）

**架構**
```
你的電腦（Windows 可）
  ├─ agentchattr 伺服器（Python FastAPI，網頁介面 localhost:8300）
  │    └─ 資料：訊息（JSONL）、Job、規則、摘要、頻道、排程
  ├─ wrapper → Claude Code（你的 Claude 訂閱登入）
  ├─ wrapper → Codex CLI（你的 ChatGPT 訂閱登入）
  └─ wrapper → Gemini CLI（你的 Google 帳號）
  代理透過 MCP 讀取和發送聊天訊息
```

**對照計劃需求**

| 計劃需求 | 狀態 | 說明 |
|---|---|---|
| 真人與多個 AI 同一聊天室 | ✅ | |
| AI 直接互相對話 | ✅ | @ 對方，伺服器自動把提示打進對方的終端機 |
| 防止無限對話 | ✅ | `max_agent_hops = 4`，超過就暫停，打 `/continue` 繼續 |
| 討論轉成任務 | ✅ | 訊息可轉成 Job，AI 也能提議 Job，由你接受或駁回 |
| 任務狀態 | 🟡 | 只有 To Do→Active→Closed，要擴充成計劃的完整狀態 |
| 交叉審查 | 🟡 | 有審查範本，但沒有 PASS／FAIL 和修正次數上限 |
| 成果回傳 | 🟡 | AI 在聊天室回報；沒有和 GitHub PR 正式綁定 |
| 重大操作人工批准 | ❌ | 要靠 GitHub 分支保護，加上代理本身的權限模式 |
| 持久保存 | ✅ | 重開機後保留；附件要另外備份 |
| 多聊天室或專案隔離 | 🟡 | 有多頻道，但所有代理共用同一台機器的權限 |
| 手機使用 | ❌ | 只能本機 |
| 安全 | 🟡 | 每次啟動產生權杖、只接受本機連線；**「自動核准」模式等同讓 AI 任意執行指令** |

## 四、建議架構（分兩段）

### 第一段：P1～P3，本機版（agentchattr）
- 在你的 Windows 電腦上跑 agentchattr，加入 Claude Code、Codex 兩個代理。
- 用一個**測試用 GitHub 倉庫**，不碰正式專案。
- 代理**不開自動核准**；危險操作由你在代理的終端機逐次允許。
- 成果一律開 PR，合併由你在 GitHub 操作（設定分支保護）。

### 第二段：P4～P6，遠端加手機（二選一，實測後決定）
- **路線 A：擴充 agentchattr。** 加上 HTTPS 和登入，或用 VPN（例如開源的 Headscale／WireGuard）從手機連回家裡電腦。工作量小，但電腦要一直開著。
- **路線 B：Matrix＋自建橋接器。** Matrix 伺服器負責聊天室和手機 App；自己寫一個橋接器，用 agentapi 呼叫各家 CLI，再加上任務狀態機、審查流程和修正次數上限。工作量大，但最接近計劃的完整願景，也方便部署到 VPS。

## 五、需要自行開發的部分（不論哪條路線）

1. **任務狀態機**：待討論→已指派→執行中→已提交→審查中→通過／退回→等待核准→已完成，外加失敗、取消、阻塞。
2. **審查流程**：PASS／FAIL／BLOCKED／NOT_TESTED 固定格式，以及最大修正次數。
3. **GitHub 綁定**：任務對應分支和 PR，審查讀的是 PR 實際內容，不是 AI 的口頭報告。
4. **額度管理**：偵測訂閱額度用盡，標成「等待重置」，不算任務失敗。
5. **遠端存取與身分驗證**（第二段）。

---

## 六、訂閱方案條款重點（沿用 v1 的核對）

- **Claude**：官方明文允許「end user 用自己的訂閱登入未修改的 Claude Code」。限制是只能你自己用、不能轉售；額度以「一般個人使用」為前提。**透過 Agent SDK 的轉接器（例如 Claude 的 ACP 轉接器）官方建議用 API 金鑰**，所以優先選擇直接包裝官方 CLI 的方案，例如 agentchattr、agentapi。
- **Codex**：ChatGPT Plus（US$20）含 Codex CLI，每 5 小時有額度；Pro（US$100 起）目前沒有 5 小時上限，但可能有每週上限。
- **Gemini CLI**：用 Google 帳號登入的免費或付費額度，P1 實測時一併確認。

## 八、MVP（P1 實測清單，約半天）

1. 在 Windows 安裝 Python 3.11 以上和 agentchattr。
2. 確認 Claude Code、Codex CLI 都已經用訂閱登入。
3. 開一個頻道，你、Claude、Codex 三方討論一個小需求。
4. 驗證：
   - Claude @Codex 會不會觸發 Codex？
   - 第 4 跳後會不會暫停？
   - 訊息能不能轉成 Job？
   - Codex 能不能在測試倉庫開出 PR？
   - Claude 能不能讀 PR 內容並給出審查結果？
   - 重開伺服器後，紀錄是否還在？
5. 記錄每個任務大約消耗多少訂閱額度。

**驗收條件：** 上面 6 項都有實際截圖或紀錄，未測的標成 NOT_TESTED。

## 九、P1 實測結果（2026-11-21，Windows 11，agentchattr 0.5.0）

環境：你的 Windows 電腦；Claude Code 2.1.295（Claude Pro 訂閱，Opus 5.5）；Codex CLI 0.167.0（ChatGPT 訂閱，GPT-6-Sol）；測試倉庫 `test-repo`（只在本機，未推送）。

| # | 驗證項目 | 結果 | 證據 |
|---|---|---|---|
| 1 | AI 在聊天室 @ 另一個 AI 會自動觸發對方 | **PASS** | Claude 發「@codex-2 請回答 test-repo 有哪些檔案」，Codex 自動回覆（#25→#26） |
| 2 | 防無限對話 | **PASS** | 兩個 AI 輪流數到 6，第 4 跳後出現「Loop guard: 4 agent-to-agent hops reached」並停止 |
| 3 | 討論轉成工作（Job） | **部分 PASS** | 由 AI 用工具提議工作，人按 Accept 後建立 Job（重啟後仍在）。但：介面上的「Convert to job」按鈕按兩次都沒反應；接受後 Job 沒有指派對象、狀態直接顯示 done，也沒有自動派工給 Codex |
| 4 | AI 獨立開發並交出成果 | **PASS** | Codex 在 `feature/hello` 新增 hello.py、test_hello.py，測試通過，commit `67e8b30`，主動回報並 @Claude |
| 5 | 另一個 AI 讀取實際成果交叉審查 | **PASS** | Claude 實際執行 `git diff master..feature/hello`、`python -m unittest`，以 PASS 格式回覆並列出非阻擋建議；未合併、未推送 |
| 6 | 伺服器重啟後紀錄保留 | **PASS** | 重啟後聊天紀錄（#43、審查結論、工作提案）與 jobs.json 都在，兩個代理自動重新連線 |

### 實測中遇到的問題（正式使用前要處理）

1. **Windows Terminal 不相容**：在 Windows Terminal 裡會送出多餘的 Esc，代理被跳到別的選單。改用傳統主控台（conhost）才正常。
2. **Codex 連不上聊天室工具**：
   - 透過 `codex.cmd` 啟動時，網址引號被 cmd 吃掉。改成直接啟動 `codex.exe`。
   - agentchattr 的本機轉接程式回應被改壞（多了 chunked 標頭），疑似防毒軟體（Avast 等）攔截本機 HTTP；pip 下載也出現同樣錯誤。**測試副本已修補**：讓 Codex 直接連伺服器，憑證走環境變數。
3. **身分名稱混亂**：代理被強制關閉後，伺服器保留舊名字，新實例變成 codex-2、claude-2，訊息會送到沒人讀的佇列。每次重啟要先註銷，或在介面上確認名字。
4. **人工確認太頻繁**：Codex 沙箱擋寫 `.git`、找不到系統 Python；一個小任務就要人按 5～6 次允許。改成自動模式後才順暢。
5. **AI 不能替 AI 放寬權限**：由我（主控 AI）把代理改成自動執行，兩次都被 Claude Code 的安全分類器以「Undermining Oversight」擋下，最後由你親自執行腳本切換。**這正好驗證了計劃中「重大權限變更須由真人批准」在實際環境中成立。**
6. **測試電腦的既有設定會干擾**（換電腦時請先檢查）：
   - 若使用者環境變數 `ANTHROPIC_MODEL`／`ANTHROPIC_BASE_URL` 指向本機模型（例如 Ollama），Claude Code 會改接該模型而不是 Claude。
   - 若 Codex 全域設定為「永不詢問＋完整存取」，代理會在無人確認下執行。
   - 若 Claude Code 執行檔被第三方外掛修改，與訂閱條款要求的「未修改版本」衝突，要先處理。
7. **只能在本機**：網頁介面只接受本機連線，沒有手機版。
8. **額度消耗**：從 20:14 到 20:47，Codex 的 5 小時額度從 50% 降到 38%（Plus 方案；20:14 以前的用量無法區分是否來自這次測試）。一個小型開發任務加審查，大約用掉 5～10%。

### 結論
agentchattr 已經能做到「真人＋Claude＋Codex 同群討論 → AI 互相 @ → 開發 → 交叉審查 → 紀錄保留」的核心流程。**但它還是偏實驗性的工具**：Windows 相容性、身分管理、任務派工都要修補。建議的下一步：
- **短期**：保留 agentchattr 當原型，把上面第 1～4 點的修補整理成啟動腳本。
- **中期（P2～P5）**：任務狀態機、PASS/FAIL 修正次數上限、GitHub PR 綁定改為自己開發，並評估改用 Matrix 加自建橋接器，以取得手機版和遠端存取。

測試用的修補都在 `agentchattr/` 副本：`wrapper.py` 的 `codex_direct` 模式、`mcp_proxy.py` 的 `_safe_read`、`config.toml` 的代理路徑。

### 一鍵啟動與停止（已實測）

| 檔案 | 用途 |
|---|---|
| `agentchattr/start-chat.bat` | 雙擊啟動：伺服器和兩個代理都在**背景執行，不開視窗**，並自動打開聊天室網頁。預設為自動模式 |
| `start-chat.bat -Safe` | 安全模式：代理每次改檔案或跑指令前都會問你，聊天室工具則一律允許 |
| `start-chat.bat -Visible` | 顯示代理視窗，方便觀察 |
| `agentchattr/show-agents.bat` | 把背景的代理視窗叫出來；AI 卡住、在等你確認時使用。`-Hide` 會再藏回背景 |
| `agentchattr/stop-chat.bat` | 雙擊一鍵關閉：只關閉這個資料夾啟動的程式，不會動到其他程式 |

啟動時會自動處理：
- 重設代理身分，名字固定為 `claude` 和 `codex`，舊的身分檔會移到 `data/old/`。
- 忽略會讓 Claude Code 改接本機模型的 `ANTHROPIC_*` 環境變數（只在這次啟動生效）。
- 一律使用傳統主控台視窗。
- 聊天紀錄會保留。
